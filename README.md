# RevitServer-Synx

Графическая диагностика и точечный ремонт кэша Autodesk Revit Server Accelerator после аварийного выключения, зависания AutoSync или ошибок синхронизации отдельных моделей.

Также программа исправляет системную причину повторных зависаний после смены DNS/IP-адреса Revit Server Host: старые адреса в `HostNodeForCachedModels.db3` заменяются сразу для всех затронутых GUID с сохранением портов.

Обычное открытие программы ничего не изменяет. Ремонт выполняется только для выбранной модели после отдельного подтверждения.

## Быстрый запуск с GitHub

Откройте **Windows PowerShell от имени администратора** и выполните:

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
irm https://raw.githubusercontent.com/viendhyra/RevitServer-Synx/main/Run.ps1 | iex
```

Команда загружает временную копию программы в `%TEMP%` и открывает графический интерфейс. Установка не требуется.

Более безопасный запуск с предварительным просмотром загрузчика:

```powershell
$url = 'https://raw.githubusercontent.com/viendhyra/RevitServer-Synx/main/Run.ps1'
$file = "$env:TEMP\Run-RevitServer-Synx.ps1"
Invoke-WebRequest -UseBasicParsing $url -OutFile $file
notepad $file
& $file
```

## Что проверяется

- установленные экземпляры `Revit Server 20xx` в `%ProgramData%\Autodesk`;
- `AutoSyncLog.log` и повторения `threads are still not done for Model`;
- GUID зависших моделей и номера циклов AutoSync;
- имя и RSN-путь модели из `Projects\ModelLocationTable.db3`;
- ошибки разрешения HostNode/IP;
- `HostNodeForCachedModels.db3` и привязки GUID → Host;
- `LocalServer_Cache.db3` и `CacheStatus`;
- целостность обеих SQLite-баз;
- наличие каталога `Cache\<GUID>`;
- осиротевшие каталоги без записи в базе.
- собственную историю найденных сбоев и ремонтов каждого GUID.
- разные старые Host-адреса, число связанных с ними GUID и используемые порты;
- доступность нового Host по DNS/IP и каждому используемому порту;
- нулевые и недоступные для чтения файлы внутри кэша выбранной модели.

Используется встроенная библиотека Windows `winsqlite3.dll`; Python и отдельный `sqlite3.exe` не требуются.

## Как выполняется ремонт

После выбора модели и нажатия **«Исправить выбранную»** программа:

1. сохраняет состояние служб и IIS-пулов;
2. останавливает Revit Server AutoSync выбранной версии;
3. останавливает соответствующий `RevitServerAppPool20xx`;
4. создаёт резервную копию обеих `.db3` и служебных journal/WAL-файлов;
5. проверяет размер и SHA-256 резервных копий баз;
6. удаляет из активной системы весь каталог `Cache\<выбранный GUID>`, быстро перемещая его в `SynxQuarantine` без копирования;
7. транзакционно удаляет только выбранный GUID из `HostNodeForCachedModels.db3`;
8. выполняет `PRAGMA integrity_check`;
9. гарантированно запускает AutoSync и IIS-пул выбранной версии, даже если они остались остановлены после предыдущей ошибки;
10. создаёт отчёт и `Rollback.ps1`.

Каждый шаг показывается в окне: процент, текущая операция и журнал уже выполненных действий.

Каталог GUID перемещается атомарным переименованием на том же диске. Если Windows вернёт `Access denied`, программа меняет владельца и выдаёт группе администраторов права только на точно проверенный `Cache\<GUID>`, после чего повторяет операцию.

Если после остановки IIS-пула остался его рабочий процесс `w3wp.exe`, программа завершает только процесс выбранного пула Revit Server и повторяет перенос. Состояние IIS читается совместимо с разными версиями модуля `WebAdministration`.

Если шаг завершается ошибкой, программа пытается автоматически восстановить базу, каталог кэша и состояние компонентов.

Если в таблице несколько строк со статусом `ЗАВИСАНИЕ`, кнопка **«Исправить все зависшие»** после одного подтверждения последовательно обработает их все. Для каждой модели создаётся отдельный бэкап базы и каталог карантина; в окне показываются номер модели и общий прогресс.

Центральная модель на Revit Server Host, её имя, GUID и ссылки из других проектов не изменяются. При следующем обращении Accelerator заново получает кэш модели с Host.

## Исправление после смены адреса Host

Если Revit Server Host получил новый DNS/IP, пока Accelerator продолжал работать, точечное удаление кэша может не помочь: GUID остаётся прежним, а локальная таблица `HostNodeForCachedModels` продолжает направлять его на старый адрес.

В верхней панели программы:

1. нажмите **«Прочитать логи и базы»**;
2. выберите устаревший адрес в поле **«Старый Host»**;
3. введите новый DNS/IP без `http://` и пути;
4. нажмите **«Проверить адрес»** — миграция разрешается только после успешного DNS/IP-разрешения и TCP-проверки всех используемых портов;
5. нажмите **«Исправить адрес и кэши»** и подтвердите список моделей.

Программа одним согласованным действием останавливает AutoSync и IIS-пул, создаёт проверенный бэкап SQLite, формирует отчёты о файлах кэша, перемещает в карантин кэши **всех** GUID старого Host, транзакционно заменяет адрес с сохранением порта каждой записи, проверяет результат и запускает компоненты. Если любой шаг не выполнен, базы и уже перемещённые каталоги возвращаются обратно.

Например, `185.77.240.202:36942` станет `new-host.example.local:36942`, а запись с портом `36943` сохранит именно `36943`.

Не запускайте для этой ситуации последовательный ремонт отдельных GUID: пока в базе остаётся старый Host, новый кэш может снова начать загружаться по неверному маршруту.

## Состояния в таблице

- `OK` — ошибок по модели не найдено;
- `ЗАВИСАНИЕ` — AutoSync не завершил обработку модели минимум три раза;
- `ОШИБКА` — в логе найдена ошибка выбранного GUID;
- `НЕТ КЭША` — запись базы есть, каталога GUID нет;
- `БЕЗ ЗАПИСИ БД` — каталог GUID есть, привязки к HostNode нет.

Revit Server хранит в локальной базе Accelerator GUID и HostNode, но не читаемое имя RVT. Поэтому надёжный основной идентификатор — GUID из `AutoSyncLog` и каталога `Cache`.

Для имени программа автоматически читает `%ProgramData%\Autodesk\Revit Server 20xx\Projects\ModelLocationTable.db3`. Если Accelerator и Host стоят на разных серверах, скопируйте `ModelLocationTable.db3` с Host и выберите её кнопкой **«База имён…»**. Эта база используется только для чтения и не изменяется при ремонте.

Кнопка **«Получить имена с Host»** пробует безопасно скопировать соответствующую базу через административный ресурс `\\HOST\c$\ProgramData\Autodesk\Revit Server 20xx\Projects\ModelLocationTable.db3` в `SynxBackup\NameSources`, проверить её целостность и сопоставить имена по GUID. Учётной записи нужен доступ к `C$` на Host. Если доступ закрыт, используйте **«База имён…»** и выберите копию файла вручную. База имён должна быть именно с того Host: файл другого сервера может содержать другие GUID и не даст совпадений.

## Проверка файлов кэша

Кнопка **«Глубокая диагностика»** создаёт JSON-отчёт в `SynxBackup\ModelDiagnostics`. В него входят:

- количество и общий объём файлов кэша;
- нулевые и недоступные для чтения файлы;
- `PRAGMA integrity_check` для `Data_Sync.db3`, `Data_Sync_DataAccessSession.db3` и других внутренних SQLite-баз;
- оставшиеся journal/WAL/SHM-файлы транзакций;
- 20 последних изменённых `.rws`, `.dat` и `.db3` с точным временем;
- контекст строк `AutoSyncLog` вокруг выбранного GUID;
- отдельное предупреждение, если тот же GUID повторно завис после полной очистки локального кэша.

При миграции краткие файловые отчёты автоматически создаются для каждого затронутого GUID в каталоге операции.

Формат содержимого кэша является внутренним форматом Autodesk. Поэтому успешное чтение файла не доказывает, что его содержимое семантически корректно. Если файловых ошибок нет, но загрузка зависает после смены адреса, главным диагностическим признаком остаётся устаревшая привязка GUID → HostNode и ошибки `Failed to get IP addresses`/`threads are still not done` в AutoSyncLog.

Если адрес и порты правильные, внутренние SQLite-базы исправны, но **тот же GUID после удаления и новой загрузки снова зависает**, повторное удаление кэша обычно не устраняет источник. Это указывает на данные, которые заново приходят с Host, на зависшую обработку ModelService либо на центральную модель. В таком случае сохраните отчёт диагностики и создайте новую центральную модель штатно через Revit (`Save As`/пересохранение на Revit Server). Программа не изменяет файлы центральной модели напрямую.

## Требования

- Windows Server 2016/2019/2022/2025 или совместимая Windows;
- Windows PowerShell 5.1;
- Autodesk Revit Server Accelerator;
- права администратора для ремонта;
- модуль IIS `WebAdministration`;
- доступ к `raw.githubusercontent.com` для запуска с GitHub.

Без прав администратора интерфейс работает в режиме просмотра.

## Резервные копии

Для каждой версии Revit Server создаётся отдельная папка рядом с `Cache`, `Logs` и `Projects`:

```text
%ProgramData%\Autodesk\Revit Server 2022\SynxBackup\Repair_<GUID>_<дата>\DatabaseBackup
```

Для массовой смены Host:

```text
%ProgramData%\Autodesk\Revit Server 2022\SynxBackup\HostMigration_<старый>_to_<новый>_<дата>\DatabaseBackup
```

В `DatabaseBackup` сохраняются только файлы SQLite (`.db3`, journal/WAL/SHM). Кэш модели в эту папку не копируется.

В корне `SynxBackup` ведётся постоянный журнал:

```text
%ProgramData%\Autodesk\Revit Server 2022\SynxBackup\SynxIncidentHistory.jsonl
```

Он содержит дату, GUID, имя и путь модели, тип ошибки, количество зависаний, успешные и неудачные ремонты. Кнопка **«Журнал Synx»** открывает этот файл. После успешного ремонта старые строки AutoSync не считаются новой ошибкой. Если для того же GUID появляется более новая ошибка, строка поднимается вверх, окрашивается красным и получает отметку `ПОВТОР`.

Карантин располагается рядом с экземпляром Revit Server:

```text
%ProgramData%\Autodesk\Revit Server 2022\SynxQuarantine
```

Не удаляйте карантин до успешной проверки открытия и синхронизации модели.

Кэш не дублируется в папку резервной копии. Каталог выбранного GUID только перемещается на том же диске, поэтому операция выполняется быстро и не требует места для второй копии модели.

## Проверка после ремонта

1. Нажмите **«Прочитать логи и базы»** повторно.
2. Откройте модель через Accelerator.
3. Выполните синхронизацию с центральной моделью.
4. Убедитесь, что в новом фрагменте `AutoSyncLog.log` нет повторяющегося зависания этого GUID.
5. После проверки можно удалить старый каталог из `SynxQuarantine`.
